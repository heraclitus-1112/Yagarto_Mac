# 汇编源码旧编码导入设计

## 背景与目标

当前工程创建器和工程导航器都只接受严格 UTF-8。课程资料中的旧版汇编源码常由 Windows 或早期编辑器保存为 GBK/GB18030、Windows-1252 或 ISO-8859-1，因此文件本身有效，却会被报告为“源码不是有效的 UTF-8 文本”。实际样本 `td52a.s` 是西文单字节编码，包含法语重音注释。

本次目标是在不降低现有文件安全边界的前提下，让两个外部源码入口无损接受 UTF-8、GBK/GB18030 和常见西文旧编码，并把工程内部副本统一保存为 UTF-8。

## 方案选择

采用受限自动识别，而不是按固定顺序盲目尝试或要求用户每次手动选编码：

1. 首先严格按 UTF-8 解码；ASCII 自然包含在此路径中。
2. UTF-8 失败时调用 Foundation 的无损编码识别。
3. 只接受 GB18030、Windows-1252 和 ISO-8859-1；其他识别结果继续拒绝。
4. 拒绝 NUL、Unicode 替换字符以及除制表、换行、回车之外的控制字符，避免把任意二进制误判成文本。
5. 成功解码后统一用 UTF-8 重新编码，不改变 CRLF/LF 等文本内容。

这一方案能区分当前法语样本和 GB18030 中文样本，又不会让“Latin-1 可解释任意字节”的特性绕过二进制检查。

## 组件与数据流

在 `YagartoCore` 新增独立的 `SourceTextDecoder`：输入安全读取后的 `Data`，输出文本、UTF-8 数据和识别出的来源编码。编码展示名称由核心层统一提供，避免两个导入入口各自实现判定。

批量“导入现有源码”继续使用 `ProjectCreator` 的暂存、原子发布和原文件不变性复核流程。入口符号从解码后的文本检测，暂存工程写入 UTF-8 数据；工程成功发布后，仍按既有语义迁移原文件。若编码发生转换，导入报告增加 `project.encoding_converted` 警告；若原文件删除同时失败，两条警告都保留。

工程导航器“添加现有汇编文件”由 `LocalProjectSourceManager` 调用同一解码器。外部文件保持不变，工程副本写成 UTF-8；`ProjectSourceMutationResult` 返回发生转换的相对路径，完成提示列出这些文件。

## 安全与错误处理

编码识别发生在现有普通文件、非符号链接、非硬链接和 4 MiB 上限检查之后。批量复制仍是全有或全无；任何文件无法无损识别时，不发布任何文件或配置变更。无法识别或疑似二进制的输入继续使用现有无效文本错误，不暴露模糊的自动修复。

## 测试与验收

- 解码器单元测试覆盖 UTF-8、GB18030 中文、Windows-1252/Latin-1 法语、NUL/控制字符和无法识别数据。
- `ProjectCreatorTests` 验证旧编码文件被写成 UTF-8、入口检测成功、转换警告存在并保持既有原文件迁移语义。
- `ProjectSourceManagerTests` 验证添加文件时外部原件字节不变、工程副本为 UTF-8、转换路径被报告，并继续验证批量回滚。
- 定向运行解码器、工程创建器、源码管理器和相关 ViewModel/契约测试；收尾运行一次严格 Debug 测试与 Release 构建，不重复执行 XCUITest。
